## Context

See proposal.md - Why/What Changes for motivation and scope. Relevant current-state facts that shape this design:

- Every screen (`login/chrome/screen_*.go`) matches on DOM selectors only (`CurrentPageMatches`), never on URL or hostname - except `firstScreen` (always matches, just navigates + seeds cookies) and `finalScreen` (matches on URL path `/home`). This means a fixture only has to contain the right elements at the right ids; it does not need to be served from any particular hostname.
- `credentialsScreen`, `otpScreen`, and `trustedDeviceScreen` all return `ShouldWaitForResponse() == true`, so `resolve()` drives them through `chromedp.RunResponse`, which waits for a real network response to the navigation triggered by `Do()`. A same-origin form POST that the mock server itself answers satisfies this the same way the live site does; nothing about `RunResponse` needs to change.
- `login/chrome` never uses a Go `net/http` client/`RoundTripper` in the path of screen navigation: every page/form/asset fetch happens inside the real Chrome process driven over CDP (`chromedp`). The package's only `net/http` usage is `http.Cookie`/`http.SameSite` value types and an unrelated optional client in `WithChromeVersion` for downloading the Chrome binary. So there is no Go-level HTTP client/transport seam to inject a mock into; both capture and hostname redirection have to happen at the CDP/browser layer instead (CDP network-response capture, and Chrome's `--host-resolver-rules` launch flag).
- Real captured markup will contain absolute `action`/`href`/`src` attributes pointing at the real site's hostnames (`integration.moncompte.laposte.fr`, `secure.interop.digiposte.io`, `auth.interop.digiposte.io`, `www.digiposte.fr`, ...). If served verbatim without redirecting those hostnames somewhere local, a browser driven against the mock server would still submit forms and load assets against those real hosts - defeating the whole point and recreating today's rate-limit risk. Handling this is a first-class part of this design, not a detail.
- `finalScreen.Do` reads `sessionStorage.getItem("access_token")`/`"app_expires_at"` and real cookies via CDP - values a captured `/home` page never contains verbatim (they're set by JS after a real token exchange this design does not replicate).
- `login/chrome` already has one precedent for an on-disk debug artifact produced during a real run: `WithScreenShortOnError` (`screenshot.go`), which saves a PNG on failure and is a genuine production debugging feature exposed as a public option. The new capture mechanism is different in kind - it is a maintainer-only fixture-generation tool with no use to a library consumer - so it does not follow that public-option precedent (see Decision 1).

## Goals / Non-Goals

**Goals:**
- Let `login/chrome`'s screen selectors and interactions be exercised by a real chromedp/Chrome instance against static local content, with no live account, no live browser session against the real site, and no network access to the real site.
- Make it easy to re-capture fixtures by hand when the real site's markup drifts (this has already happened twice: OTP's `#submit-button` and trusted-device's `#save-trusted-device-later`).
- Keep the capture mechanism reusable non-throwaway code (an option + helper), not a one-off script that bit-rots.

**Non-Goals:**
- Replicating the real OAuth/token-exchange or OTP-validation server logic. The mock server only needs to get each `Screen`'s `Do()` to succeed and move on to the next screen; it does not need to validate credentials or OTP codes the way the real backend does.
- Automatically detecting when fixtures have drifted from the real site. That would require periodically hitting the live site, which is exactly what this change avoids doing more of. Drift detection stays manual (a maintainer notices a live spec failure and re-captures).
- Changing anything about `login/chrome`'s production behavior, its public API (beyond the one new debug-only option below), or `chrome_test.go`'s existing live specs.

## Decisions

**1. Capture via a test-only `export_test.go` helper and CDP network-response recording, not a public option or a standalone script.**
`WithScreenDumpDir` is a maintainer-only fixture-generation tool with no use to a library consumer (unlike `WithScreenShortOnError`), so it must not be public API. It is declared in a new `login/chrome/export_test.go` (internal `package chrome`, `_test.go` file): exported (capitalized) so the external `package chrome_test` capture spec can call it during `go test`, but non-existent in a normal build - Go's `_test.go` files are excluded from `go build`/`go get`, so the symbol never ships. It wires an unexported `screenDumpDir` field through `chromeLogin`/`Screens` exactly as a public option would, via the same `login.Option`/`Apply` mechanism `chrome.New` already uses.
When set, instead of dumping only `document.documentElement.outerHTML`, `Screens.run` enables CDP's `Network` domain and records every response for the current navigation - the document and every asset it loads (CSS/JS/images) - to `<dir>/<hostname>/<path>`, mirroring each response's real hostname and URL path. This captures assets automatically as a side effect of capturing the document, instead of requiring a second pass.
This reuses `chrome_test.go`'s existing live, credential-gated spec to do the actual capture run (a maintainer calls the test-only helper and runs the existing "Should work" spec once against a live account), instead of introducing a second, parallel way to drive a login.
*Alternatives considered*: a public `login.Option` (rejected - no consumer use, pollutes the API surface); a separate `cmd/`-style capture binary (rejected - duplicates `chrome.New`'s option wiring and the existing live spec's credential/skip handling for no real benefit); a Go `net/http` client/`RoundTripper` hook (not applicable - see Context, there is no Go HTTP client in this path to hook).

**2. Fixtures are captured raw; hostname redirection happens at serve time via Chrome's own DNS override, not via rewriting fixture content.**
`login/chrome/testdata/<hostname>/...` store exactly what the capture helper wrote - byte-for-byte real responses, organized by the hostname that served them. The mock HTTP server (new test helper, `login/chrome/mock_server_test.go`) does not rewrite any URL or attribute inside the fixtures. Instead, the browser under test is launched with Chrome's `--host-resolver-rules` flag mapping each of the flow's known real hostnames to the mock server's own `127.0.0.1:<port>`; Chrome still sends the original `Host` header, so the server dispatches each incoming request by `Host` + path to that hostname's captured tree and serves the matching response verbatim. A request for any hostname with no captured tree is refused (not proxied, not passed through), so an unanticipated real reference fails the test loudly instead of leaking a live network call.
*Rationale*: keeps re-captured fixtures diffable against the previous version (pure markup/asset drift, nothing mixed in), and keeps the entire hostname allow-list in one reviewable place (the host-resolver-rules mapping) instead of a rewrite rule repeated by hand across fixtures.
*Alternative considered*: rewrite absolute references to relative/synthetic paths at serve time. Rejected - real pages reference their own assets by real absolute or host-relative URLs in ways that are easy to miss rewriting (inline JS building URLs, `srcset`, etc.); redirecting the hostname itself at the DNS/Host level is robust to all of those without inspecting page content at all.

**3. The final screen's fixture gets one hand-authored addition: an inline script seeding fake session state.**
`testdata/<hostname-serving-/home>/home.html` (or equivalent captured path) is the captured `/home` page plus one added `<script>` block (clearly delimited with a comment) that sets `sessionStorage.access_token`/`app_expires_at` to fixed test values and lets the mock server's cookie response set a matching test cookie. This is the one fixture that cannot be "just" a raw capture, because the real page's token is set by live JS this design intentionally does not replicate (Non-Goals). The rest of the file stays a real capture so `finalScreen.CurrentPageMatches`'s URL-path check keeps being exercised against real markup/routing.

**4. The mock server dispatches by real hostname + path, mirroring captured storage - it does not synthesize a flow-order route sequence.**
Because fixtures are stored and served under their real hostname and path (Decisions 1-2), the multi-step login pages naturally chain together the same way they do on the real site: each captured page's own (unrewritten) `action`/`href` already points at the next real path, which the browser now reaches via the host-resolver override instead of the real network. One caveat, called out as an assumption rather than solved generically: the credentials/OTP/trusted-device steps may be served by the real site at the *same* URL path (a Keycloak-style flow keyed by a session/execution query parameter, not by path), which would collide if storage mirrored the exact path. Where that happens, the capture helper names that hostname's multi-step pages descriptively (`credentials.html`, `otp.html`, `trusted-device.html`) instead of mirroring the literal dynamic path; assets keep their real relative path since those are stable and unique. If this assumption turns out wrong once real captures are taken, revisit this decision before continuing past task 1 of tasks.md.

**5. New specs live alongside the existing ones, using the same `chrome.New` entry point.**
A new `login/chrome/mock_test.go` (external test package, like `chrome_test.go`) starts the mock server, then calls `chrome.New(chrome.WithURL(mockServer.URL), ...)` and asserts the same kind of outcome `chrome_test.go`'s "Should work" spec does (valid token, non-empty cookies). No test-only seam is added to production code beyond the one new option in Decision 1; the mock server and its sanitizer are entirely test-package code.

## Risks / Trade-offs

- **[Risk] A fixture references a hostname not in the host-resolver-rules allow-list (a new external script, a hardcoded API host in inline JS, etc.), and that hostname resolves to the real internet instead of the mock server.** → Mitigation: the allow-list is a fixed, reviewable set of the flow's known hostnames; any other hostname is not remapped, so Chrome's normal DNS resolution applies and the request goes out to the real internet over the test runner's normal network - to fully close this off, `chromedp` is also configured to block all network requests whose host is not in that same allow-list, so an unanticipated reference fails the test loudly (blocked request/timeout) rather than silently reaching a live server.
- **[Risk] The credentials/OTP/trusted-device steps share one real URL path on the SSO hostname (Decision 4's caveat), so capturing later steps could overwrite an earlier one if storage mirrored the literal path.** → Mitigation: the capture helper names those pages descriptively rather than by literal path (Decision 4); this is flagged as an assumption to confirm against the first real capture (task 1 in tasks.md), not yet verified against the real site.
- **[Risk] Fixtures drift silently from the real site between the (manual, infrequent) re-captures, so mock-based specs keep passing while the real site has moved on.** → Mitigation: this is explicitly accepted (Non-Goals) - `chrome_test.go`'s live specs remain the source of truth for real-site compatibility; the new specs are a fast complement for the parts that don't need a live account, not a replacement.
- **[Trade-off] The final screen's fixture is partly hand-authored rather than a pure capture.** → Accepted: the alternative (replicating real token-exchange logic in the mock server) is far more complex for no added confidence in `login/chrome`'s own code, which never inspects how the token got into `sessionStorage`.

## Migration Plan

1. Add the test-only capture helper in `export_test.go` (Decision 1); no production code or public API changes.
2. Use it once, manually, against a live account to produce the initial `testdata/<hostname>/...` fixtures (pages + assets); hand-add the final screen's session-seeding script (Decision 3); confirm or revisit the path-collision assumption in Decision 4 against what was actually captured.
3. Add the mock server test helper (Decisions 2 and 4) and the new specs (Decision 5).
4. Wire the new specs into `.github/workflows/test.yml` as an unconditional step (no live secrets needed), alongside (not replacing) the existing live `v1`/`login/chrome` step.
No rollback concerns: everything here is additive test/tooling surface; reverting is deleting the new option, fixtures, and specs.
